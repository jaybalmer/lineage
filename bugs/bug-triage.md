## How the loop works

0. **Reconcile (first thing each run).** Before reading any email, the triage task checks for build sessions that shipped since the last run by reading the git log on `main` (`git log main --since=...`, or the merged-PR list). It looks at every merged PR, not just bug ones: `BUG-NNN` ids mark bug sessions, `feat`/`fix`/`chore` subjects with a `(#NN)` mark feature and chore sessions. For each shipped session it: (a) moves any BUG ids from the **Queue** to **Shipped** with the PR number, (b) reconciles `bugs/SHIP-LOG.md` (flip the matching `status: pending` entry to `status: merged` with the PR number and squash sha; expand any `PENDING auto-stub` the SessionEnd hook left into a one-line summary; add an entry for any merged PR that has none, which is how feature sessions get recorded since they carry no `BUG-NNN`), (c) archives the matching `NEXT-SESSION.md` brief to `bugs/archive/<date>-<slug>.md`, and (d) resets `NEXT-SESSION.md` to "NO BUILD-READY BRIEF YET" (or to the next candidate cluster). This is what keeps the Queue, the brief, and the ship log from going stale; skipping it is how a shipped session gets re-handed as the "top item." Claude Code deliberately does NOT touch the **Shipped** section here, and only ever leaves SHIP-LOG entries as `pending`; this reconcile is the only thing that flips them and closes the loop. SHIP-LOG is append-only, so never rewrite earlier entries beyond the pending-to-merged flip.
1. **Capture.** A bug lands in Gmail (see Intake below). The bridge in `Operations/gmail-bug-attachments-bridge.md` auto-saves its attachments to Drive, then marks the email read, archives it out of the inbox, and files it under the `linestry/bugs` label. The inbox stays clear; triage still finds the emails by search.
2. **Triage.** A scheduled Cowork task runs each morning: reconciles shipped work (step 0), then reads new bug emails, reviews any attached screenshots from the Drive folder, dedupes against this file, assigns severity, clusters related reports, and updates the **Queue** below.
3. **Prep + auto-draft.** Each cluster gets a Claude Code mini-brief here (format at the bottom). Then the triage task auto-drafts a self-contained, build-ready brief for **every ready cluster** as a dated file in `bugs/<YYYY-MM-DD>-<slug>.md`, so a code session can start with no further writing. A cluster is "ready" when it is a bug-fix-shaped repair or polish job; clusters needing a strategic product call or a feature build are left flagged in the Queue ("needs decision" / "separate session") rather than drafted. When a ready cluster carries a product or design choice, the brief does NOT block: it picks a sensible recommended default and surfaces it in a "DECISIONS (review before building)" block at the top of the brief, with the alternative noted, so Jay can override before the session without anything waiting on him.
4. **Fix.** Jay opens `NEXT-SESSION.md` (it points at the lead brief and lists the rest), optionally overrides a flagged decision, and hands the cluster to Claude Code; Claude Code ships a PR that names the BUG ids in its title or commit message. The NEXT morning's reconcile (step 0) reads that PR and marks the bugs done here. The id naming is the signal that makes the reconcile automatic.

5. **Regenerate the readable dashboard.** As the final step of every run, after this file and `NEXT-SESSION.md` are saved, run `python3 bugs/render-queue.py`. It parses this file's Queue + Shipped sections (and the lead from `NEXT-SESSION.md`) and rewrites `bugs/bug-queue.html`, the styled snapshot Jay opens. It is stdlib-only, scrubs em/en dashes, and derives the group, counts, lead, and next-free-id automatically, so the HTML never drifts from this markdown. Do not hand-edit `bug-queue.html`; edit the markdown and re-run the script.

Visual review depends on the Gmail-to-Drive bridge being set up once. See `Operations/gmail-bug-attachments-bridge.md`. Until then, triage runs on email text only.

Manual run any time: just say "run bug triage" in a Cowork session.

## Intake (how bugs get in)

Three ways, all landing in the same pipeline:

- **In-app widget (shipped, PR #46):** signed-in users report from the avatar dropdown; logged-out visitors from the "Sign in" menu. Each report persists a `bug_reports` row and emails a structured `[Linestry Bug]` report to jay@lineage.community (with a PostHog replay link), so it flows through the bridge and triage like any other. This is now the primary intake.
- **Subject convention (manual, no setup):** email or forward to jay@lineage.community with `[Linestry Bug]` at the start of the subject line. The triage task searches for this.
- **Gmail label (optional, needs one-time setup):** create a `linestry/bugs` label in Gmail plus a filter that applies it to anything with `[Linestry Bug]` in the subject. The triage task will also pick up `label:linestry/bugs`.

**Connector note:** the daily triage task reads the connected Gmail account, which is jay@lineage.community. No extra setup needed for the automated read.

**What a good report includes** (paste this to advisors):

> Found a bug? Email jay@lineage.community with `[Linestry Bug]` in the subject. In the body tell me:
> 1. What you were trying to do
> 2. What happened instead
> 3. The page URL (copy from the address bar)
> 4. Roughly what time it happened (so we can find the session replay)
> 5. Phone or computer, and which browser
> A screenshot or screen recording helps a lot.

(The in-app widget captures 3 to 5 automatically, so reports through it already arrive complete. Shipped via PR #46.)

## Severity rubric

| Level | Definition | Examples | Target |
|---|---|---|---|
| **P0** | Data loss, auth broken, or page will not load. Blocks core use. | Cannot sign in, timeline wipes on save, white screen on load | Same-day |
| **P1** | Core flow broken but a workaround exists. | Add Story fails on first try but works on retry, tag does not save | Within 2 to 3 days |
| **P2** | Cosmetic, edge case, or polish. | Misaligned card on mobile, wrong date format, typo | Batch when convenient |

**Repro flag** on every item: `reproducible` (clear steps) or `needs-info` (vague, parked until clarified). `needs-info` items do not enter the active queue until someone can reproduce them or the reporter answers a follow-up.

>
> **(1) Sentry, not a person, caught it.** `QuotaExceededError` out of `addClaim` on `/snowboarding/boards`, signed-in iPhone, release `cdb0224`. The boards page is where it happened to fire, not where it lives. The real fault is that `userEntities` is persisted to localStorage and, for every signed-in member, `loadDbEntities` fills it with a full mirror of `places` + `boards` + `orgs` + `events`. Measured live today: 2,599,065 characters, 4.96 MB in UTF-16, against WebKit's hard 5 MB per-origin ceiling.
>
> **(2) Zustand v5 has no `try`/`catch` around `setItem`, so this is not one broken button, it is every store action.** `set()` calls `localStorage.setItem` synchronously and lets the throw out, so `addToast`, `setMembership`, `setActivePersonId` and `setPendingTagCount` all throw too once a member is over quota. In `addClaim` the throw lands on line 1 of the action, so the DB write below it never runs and the claim is silently lost. That is why this is P0 and not the P2 a rendering-adjacent error usually is.
>
> **(3) The events import is the trigger and it is not the culprit.** `boards` alone was already 3.47 MB. PR #240 to #242 added 608 event rows, about 1.22 MB, on September 7 and 8, and the Sentry event fired hours after #242 merged. The import is fine. Persisting a four-table mirror was never fine, and it would have broken on the next catalog wave regardless.
>
> **(4) One thing to watch when building: `partialize` filters writes, not reads.** A browser that already persisted the mirror keeps hydrating it after the fix unless the persist `version` is bumped with a `migrate` alongside it. And a version bump WITHOUT a `migrate` discards the whole persisted state, which would drop `onboardingComplete` and `membership` for every existing member. Both are in the brief as D3.
>
> **(5) One side-finding, filed as BUG-189, deliberately not bundled.** `loadCatalog` and `loadDbEntities` fetch the same four tables into two slices, and every read site concatenates them without dedupe, so a signed-in member's board picker holds 7,332 rows with every board listed twice. Nobody has reported it. Fixing it means deciding what `userEntities` is supposed to mean, which is a nine-file design call, not a quota patch.

## Claude Code mini-brief format

Each cluster in the Queue carries a short brief in this shape so it is hand-off ready:

```
### BUG-NNN: <short title>  [Pn] [reproducible|needs-info]
- Reported: <date(s)>, by <who>, <count> reports
- Symptom: <what the user sees>
- Repro: <steps, or "needs-info: <what is missing>">
- Surface: <page/route, e.g. /snowboarding/profile>
- Suspected area: <best guess at the file/component/route, from CLAUDE.md knowledge>
- Session replay: <PostHog link if available, else timestamp + user to find it>
- Acceptance: <how we know it is fixed>
```

Notes for whoever drafts the brief: apply the standing no-em-dash rule. Pull suspected-area guesses from the codebase CLAUDE.md (stack, routes, gotchas) so Claude Code starts warm. When a fix ships, move the item to **Shipped** with the PR number.
